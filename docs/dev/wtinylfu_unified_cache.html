The Problem: LRU Has No Scan Resistance

Pure LRU

Before scan: LRU: [cold] ... [hot1] [hot2] [hot3] ← MRU ↑ evict One scan read: LRU: [cold] [hot1] [hot2] [hot3] [scan] ↑ evict hot1 After scan flood: LRU: [scan] [scan] [scan] [scan] [scan] all hot data evicted!

A single sequential scan evicts the entire hot working set. Every scan entry pushes one hot entry out.

The Old 20% Index Cap

Cache with index_cache_fraction = 0.2: +------------------+--------+ | row data (80%) | idx | | | (20%) | +------------------+--------+ ↑ hard cap Problem 1: Cold index wastes 20% even when no index is needed Problem 2: Hot index capped at 20% even when CK lookups need more

Static partitioning can't adapt to workload changes.

W-TinyLFU: How It Works

Three segments + a frequency sketch for admission control. Based on the Caffeine algorithm by Ben Manes.

Count-Min Sketch (frequency estimator) │ ┌─────────┐ ┌─────┴─────┐ ┌──────────┐ │ WINDOW │────▶│ ADMISSION │────▶│ PROBATION│──── touch ──▶ PROTECTED │ (1%) │ │ GATE │ │ │ (80%) └─────────┘ └───────────┘ └──────────┘ new entries freq(window) main cache hot entries enter here vs freq(prob) candidates safe here higher wins

Key Properties

Scan Resistant

Scan entries enter the tiny window (1%), compete at the admission gate, and lose to frequently-accessed probation entries. They never reach protected.

Adaptive

No static partitioning. The sketch learns access patterns and the SLRU segments auto-size based on workload. Hot data naturally migrates to protected.

Low Overhead

Count-Min Sketch uses 4-bit counters with periodic aging (halving). Protected touches skip sketch updates. ~160 fewer instructions per cache hit.

Count-Min Sketch: Frequency Estimation

key ──hash₁──▶ [ 0 3 0 1 0 2 0 0 ] row 0 ──hash₂──▶ [ 1 0 0 3 0 0 1 0 ] row 1 ──hash₃──▶ [ 0 0 4 0 1 0 0 0 ] row 2 ──hash₄──▶ [ 0 0 0 0 0 3 0 1 ] row 3 estimate(key) = min(3, 3, 4, 3) = 3 4-bit counters: saturate at 15 Aging: halve all counters periodically Width: ~1 entry per KB of cache

Admission Gate Decision

window_victim vs probation_victim:

if freq(window) > freq(probation):
    admit window → probation
    evict probation victim
else:
    evict window victim
    probation survives

// Hash-DoS protection:
if freq(window) >= 6:
    1/128 chance random admit

Aging resets every 10 × total_entries accesses, matching Caffeine's design.

Schema-Aware MVCC Routing

Multi-row partitions (tables with clustering keys) bypass the admission gate to avoid the false-rejection amplification problem.

Single-Row Partitions (no CK)

row ──▶ window ──▶ gate ──▶ probation ──▶ protected Standard W-TinyLFU path. Each partition = 1 row = 1 sketch key. Frequency tracks the partition correctly.

Multi-Row Partitions (has CK)

row ──▶ PROTECTED (direct) Bypasses window and admission gate. directly_inserted flag prevents rebalance demotion. Evicted by LRU from protected tail.

Why? If any single row from a 100-row partition is rejected by the gate, the partition is "incomplete" in cache. A 1% per-row rejection rate becomes 63% per-partition miss rate.

MVCC Safety

cache_routing_guard RAII ensures MVCC-triggered row insertions (version merges, memtable flushes) go to the correct SLRU segment. Older versions are evicted before newer versions.

Unified Index/Data Cache

SSTable index entries and row cache entries share a single LRU. The hard 20% index_cache_fraction cap is removed.

Before (separate index list)

class index_evictable : public evictable {
    lru_link_type _index_lru_link;  // +8 bytes
    bool is_index() override;      // virtual call
};

// Every add/remove/touch:
if (e.is_index()) {
    _index_list.erase(...);  // second list
}

// Reclaimer:
if (index_bytes > total * 0.20)
    force_evict_index();       // hard cap

After (unified)

using index_evictable = evictable;
// alias for backward compat

// add/remove/touch: no index check
// just the regular W-TinyLFU path

// Reclaimer:
return _lru.evict();
// hot index survives via frequency
// cold index evicted naturally

Savings: 8 bytes per index entry, no virtual dispatch on hot path, no hard cap tuning needed.

Why Hit Rates Are Similar But Latency Differs

W-TinyLFU protects entry POSITION, not just entry PRESENCE. Both policies keep the same data cached (similar hit rate). But their internal ordering differs: W-TinyLFU: PROTECTED: [hot1] [hot2] [hot3] ... [hot10000] ← safe, never disturbed WINDOW: [scan_page] ← enters here, evicted quickly LRU: LRU list: [hot_old] ... [scan] [scan] [hot_recent] [scan] ← scan entries interleave with hot entries ← hot entries pushed toward eviction front ← occasional hot entry falls off → cache miss → disk I/O ← disk I/O = tail latency spike

Even when both caches hold the same rows, W-TinyLFU's segmented structure prevents scan entries from displacing hot entries' positions. LRU's single list allows any new entry to push the oldest hot entry one step closer to eviction.

Trade-offs and Known Limitations

Advantages

  • + Scan resistance via frequency-based admission
  • + No static index/data partitioning
  • + Adaptive to workload changes
  • + 8 bytes saved per index entry
  • + No virtual dispatch on hot path
  • + MVCC-safe with schema-aware routing
  • + 29-38% tail latency improvement

Limitations

  • - Legacy MD format: 2MB index pages can flood cache
  • - Count-Min Sketch memory (~128KB default)
  • - Sketch aging cycle adds ~10 instructions per access
  • - Multi-row partitions bypass admission gate (no scan protection within large partitions)
